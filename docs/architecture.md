# Архитектура

`POST /api/v1/payments` в одной транзакции записывает платеж и событие в outbox. Уникальный индекс на `idempotency_key` устраняет дубли при параллельных запросах. Тело запроса хешируется: повтор с отличным телом получает HTTP 409.

Фоновый publisher в процессе consumer публикует ожидающие события в durable очередь `payments.new`. Записи выбираются с блокировкой `FOR UPDATE SKIP LOCKED`. После подтверждения RabbitMQ ставится `published_at`. Поэтому временная недоступность RabbitMQ не теряет событие, а сбой между подтверждением и фиксацией времени публикации может создать дубль. Consumer защищён от дублей состоянием платежа и блокировкой строки.

Один FastStream handler вызывает процессор. Процессор держит блокировку платежа во время эмуляции шлюза, сохраняет `succeeded` или `failed` и время обработки. Затем отправляет webhook. Если webhook недоступен, повторная попытка видит уже завершённый платёж и повторяет только уведомление. Три попытки разделены интервалами 1 и 2 секунды. После третьей ошибки RabbitMQ отклоняет сообщение и маршрутизирует его через `payments.dlx` в `payments.dead`.

Получатель webhook должен обеспечить идемпотентность по `event_id`: отправка и фиксация `webhook_sent_at` не являются одной транзакцией, поэтому после сетевого сбоя возможна повторная доставка.

`webhook_url` — адрес клиентского обработчика уведомлений. Сервис отправляет на него POST и считает доставку успешной только при ответе 2xx. Для ручной проверки подходит уникальный адрес сервиса сбора webhook; для реального использования нужен собственный HTTPS-обработчик клиента.
